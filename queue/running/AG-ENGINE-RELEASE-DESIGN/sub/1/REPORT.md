# Agent release capability audit (R4)

## Scope and result

Audited `astrid-agent` at exact base **`b54117c9312165e2799554ec27480665d5cad2b1`** (HEAD equals requested SHA; working tree clean) and `queue/done/I-AG-HOST-RELEASE-R4/REPORT.md`. R4 is an interface diagnosis on the unchanged base, not a producer commit. It reports Runtime `2776ba973b6c8f3555b5629b0840d9691a98d3c2`; no Runtime API candidate or Agent producer is present.

The existing Agent has useful local identities, readiness evidence, Runtime credentials, and private process-control channels, but none is an end-to-end capability that begins at verified engine readiness, survives the selected host launch/attachment, binds the later `SessionBinding`, and is revalidated by the engine supervisor at unload. In particular, startup readiness is separate from SDK host startup. The current engine release call reconnects to the local supervisor with an empty payload.

## Readiness-to-executor lifetime

- `astrid/core/generation/engine_readiness.py:613-636`: `_owned_health` creates a fresh `LinuxEngineServiceClient`, sends the install `owner_id` and launch request, and checks returned owner, install identity, launch digest, healthy state, and object-info digest. The client and channel are local variables; only returned facts and launch data survive.
- `engine_readiness.py:684-765, 790-795`: `produce_readiness` checks receipt/session evidence, does a live owned-health check, then rechecks installed session, receipt bytes, and launch marker after collecting facts. That is a bounded observation sequence, not a lock held over later host work. It does not retain a supervisor handle or prevent a subsequent owner replacement.
- `engine_readiness.py:829-863, 886-899`: the result is a serializable profile with engine/process identity and a privately written profile locator/hash. The command prints that locator; it does not return a live client/capability. The profile includes `launch_token`, daemon and engine PIDs/birth IDs, endpoint and digests (`845-852`), but these are observations in a file. The VibeComfy task binding later requires `launch_generation` (`generic_host.py:11955-11977`); the `engine_readiness.py` profile shape shown at `845-852` does not emit that key, so this audit does not treat that profile as already supplying the full binding.
- SDK startup uses `ensure_pack_host`, reached by `astrid/sdk/autobootstrap.py:507` and `services.py:111`; it does not call `run_readiness` or receive its client. Its `value` carries the Runtime worker credential, source checkout and endpoint (`host_bootstrap.py:1837-1872`). Thus the readiness producer and generic host do not share an in-memory authority object by default.
- On a later admitted task, `generic_host.py:11378-11412` creates an ordinary task `SessionBinding`; for VibeComfy, it reads the readiness-profile document at `11412-11420`, then creates the engine-specific binding at `11955-11977`. This is after host startup and task claim. It is not associated with the readiness client or supervisor under a shared owner lock.

## Supported launch and attachment modes

1. **Spawn detached host:** `host_bootstrap.py:1816-1821, 1946-1968, 2066-2107`. `ensure_pack_host` serializes host-state inspection/startup with the generic-host lock. Unless a valid healthy host is attached, it launches `astrid.core.execution.generic_host` in an owned process group with `close_fds=True`; the child gets Runtime endpoint/credential and identity/profile arguments, not a retained readiness client or engine owner capability.
2. **Attach to resident healthy host:** `host_bootstrap.py:1946-1968` optionally calls `_attach_resident_host`; matching checks include worker credential, endpoint, support root, Runtime instance/epoch, source identities and ready metadata (`1770-1813`, `1950-1966`). It returns a readiness receipt, not a channel to transfer an engine-owner capability into the existing process. Startup lock prevents competing bootstrap launches while held; it does not serialize engine owner replacement with a later release.
3. **Runtime-supervised foreground host:** `host_bootstrap.py:2074-2094, 2249-2269`. `_foreground` writes process state then executes the same generic-host CLI in the Runtime-supervised process. The ordinary child process boundary is absent, but no engine capability is passed to the CLI.
4. **Parked, Runtime-activated local host path:** `_ParkedPackHostPreparer` at `host_bootstrap.py:1297-1405` starts a host with an inherited private activation socket (`socketpair`, `pass_fds`); `acknowledge` and `await_ready` implement activation/receipt flow (`1430-1500`). The generic CLI can also take a distinct `--host-control-fd` (`generic_host.py:16543-16549, 16577-16582`) for `LocalExecutionPreparation`. This mode conveys Runtime activation/host-incarnation facts and local execution preparation. R4 does not establish it as an engine-owner release channel, and `LocalExecutionPreparation.serve_control` says the Runtime relay is pinned but “does not authenticate B” (`generic_host.py:13969-13982, 15598-15633`). It cannot be silently repurposed as an owner capability contract.

## Authentication and identity channels present

- **Runtime worker bearer credential:** owner-only credential file, actor/scopes checked as the least-privilege `astrid-pack-host` contract (`host_bootstrap.py:1837-1872`); used by `RuntimeProtocolClient` for health/registration/claims (`1891-1899`, `generic_host.py:16713-16735, 16836-16847`). The host parser also names it the worker bearer credential (`generic_host.py:16508-16511`). This authenticates the Runtime worker and its declared scopes. It is not the engine install owner token and has no Agent-to-engine release delegation.
- **Engine supervisor local channel:** `LinuxEngineServiceClient` uses a private per-install Unix socket and installation identity (`engine_custody.py:194-229, 279-311`). Readiness additionally sends the install launch token as `owner_id` for `health` and verifies the response (`engine_readiness.py:619-635, 760-765`). This is enough for readiness to query its current owner, but the fresh client is discarded. `release_owned` reconnects and sends `{}` (`engine_custody.py:328-329`), so it does not present that owner token, engine birth, or `SessionBinding`.
- **Engine HTTP endpoint:** `local_engine_endpoint` returns `http://127.0.0.1:<port>` and declares `EndpointAuth("none", None)` (`engine_local_endpoint.py:184-231`). It is status/endpoint data, not an authenticated ownership channel.
- **Private parked activation/host control:** inherited socket frames bind operation/channel and host PID/birth; grants contain executor incarnation/evidence digest (`generic_host.py:16185-16297`, `host_bootstrap.py:1365-1388, 1449-1489`). These authenticate a Runtime-mediated worker activation for that host incarnation. They do not carry or prove the engine install owner token or later binding. The separate preparation control is likewise scoped to Runtime local-execution preparation/cleanup.
- **Readiness profile:** private file plus hash gives integrity/selection for observed facts (`engine_readiness.py:856-863`; `generic_host.py:16535-16536, 16628-16657`). It is not a live authenticated channel and does not pin the supervisor through unload.

## Where `SessionBinding` is created

`SessionBinding` is an immutable observed identity (`astrid/core/execution/managed_tool_session.py:78-109`): session ID, Runtime instance, process birth, endpoint, source/config digests, execution identity, Runtime epoch, launch generation, and engine birth. Agent construction sites include:

- Wan child: `generic_host.py:6725-6742`, generated immediately before opening/starting the managed child.
- Generic admitted task: `generic_host.py:11378-11412`, after claim/task fields are available.
- VibeComfy engine session: `generic_host.py:11955-11990`, after reading readiness profile and checking required Runtime and engine-birth evidence. This is the binding relevant to the requested resident engine release.

These bindings fence managed-session admission/replacement inside `ManagedToolSession`; the type and manager do not themselves authorize a supervisor release. R4's conclusion is consistent with those source boundaries.

## Concrete race windows in the current path

1. **Readiness observation → profile publication/use:** the producer rechecks selected files at `engine_readiness.py:790-795`, then serializes/returns the profile at `829-863`. The engine owner/process can change after the final observation. There is no retained lock/handle bridging that gap.
2. **Readiness → host startup/attachment:** the SDK bootstrap is a separate path and accepts Runtime worker handoff, not a readiness result (`host_bootstrap.py:1837-1872`). An engine replacement can occur between readiness and bootstrap; host-startup locking only covers generic-host state.
3. **Host ready/attached → task claim and binding:** the host can wait resident for later claims. The task binding is formed only after a claim (`generic_host.py:11378-11412`) and the VibeComfy binding later reads the profile (`11955-11977`). Engine/session replacement can happen between profile creation and this binding, or between binding and unload; there is no supervisor-held binding association in that interval.
4. **Release request → supervisor owner selection:** `release_owned` opens a new connection and sends `{}` (`engine_custody.py:279-311, 328-329`). Supervisor identity checks bind installation fields, while the request has no owner incarnation/binding fields (`844-855`). A new supervisor for the same installation identity can therefore receive a later request; R4 explicitly notes this same-installation replacement gap.
5. **Serialized unload is not incarnation validation:** the supervisor does take `self.work` before operation and keeps it through release (`engine_custody.py:860-886`), so release is serialized against that supervisor's own stop/cleanup. Inside the lock it checks current supervisor state and calls `release`, which only accepts `{}`, checks live engine custody, inspects queue, and unloads (`803-834, 871-880`). It does not compare the verified readiness owner token, engine birth, or `SessionBinding` while holding the lock. Serialization alone does not close windows 1–4.
6. **Activation ACK uncertainty:** parked activation is one-shot (`host_bootstrap.py:1461-1464`) and binds the ACK to host incarnation, but that ACK proves activation acceptance only (`generic_host.py:16194-16204, 16281-16297`). It is not an engine release ACK and cannot resolve ownership after an unload reply is lost.

## Smallest viable Agent-owned capability path

The narrow Agent seam is the readiness producer plus the existing engine supervisor client/protocol and `GenericPackHost` construction. An Agent-owned implementation would need to: create an opaque owner-incarnation capability only after verified readiness; retain/transfer it to the exact selected host incarnation (including resident attachment); associate the later `SessionBinding`; and have the supervisor validate capability, binding, and its live engine birth **under `self.work` before queue inspection/unload**, returning a bounded ACK tied to request, binding, and incarnation. A lost/uncertain ACK must retain custody and prohibit retry against a replacement.

The current detached-child path could in principle transport an opaque descriptor at launch, but the resident-host attachment path has no corresponding registration/claim transfer; a local file/profile or reconstructed `LinuxEngineServiceClient` is not equivalent. The existing parked Runtime activation/control socket is not an agreed engine-owner operation. Therefore **there is no complete Agent-only capability path on this base that covers the supported modes**. The smallest viable next implementation is gated on a versioned, authenticated Runtime register/claim handoff for the exact host incarnation and a separately agreed Agent supervisor operation with the lock/ACK semantics above. R4 correctly declines to invent either wire contract or a Runtime API. No source was edited.
