## 3. Durable identities, ownership and states

Define `I`, the immutable original execution identity, as realm ID, run ID, task ID, attempt ID, lease ID/digest, lease fence, original Runtime epoch, executor ID plus incarnation, capability/spec/request digest, installation ID plus installation generation, canonical program/data-root binding, and supervisor enrollment/birth identity. Public views redact lease credentials. The private row retains the original binding; restarting Runtime or enrolling recovery credentials never edits `I` into a new execution identity.

Installation ID is enrolled by the owner with the installation's privileged admission gate, bound to physical roots and their filesystem identities, rather than chosen freely by a worker. Path aliases, symlinks, a different task, executor or realm cannot create another owner for the same write scope. An installation has one enrolled realm authority; cross-realm transfer requires closed prior authority or the quarantine/repair procedure. Shared roots require the same exclusion scope. The supervisor independently checks this ownership, so DB uniqueness within one realm cannot be bypassed by another realm's database.

The proposed schema must represent these logical records (SQL spelling may follow Runtime conventions):

| Record | Required durable content and constraint |
|---|---|
| Custody | Unique custody ID and unique `(realm, task, attempt)`; `I`; create idempotency scope/key and immutable canonical request SHA-256; state, version, checkpoint sequence; stable supervisor command ID and command digest; launch-gate generation; pending publication identity/bytes; evidence references/digests; recovery generation; disposition and audit linkage. Never store a public bearer recovery token. |
| Installation hold | Unique enrolled installation/write scope, independent of executor-scoped resource keys. References its custody and exact original reservations. Active custody or quarantine owns the hold; ordinary reservation expiration cannot delete it. All conflicting capabilities consult it. |
| Evidence / mutation receipts | Immutable content-addressed bytes with verified length/digest, pin ownership and quota accounting; exact request digest/result/event IDs for each mutation. Unique mutation key per custody/operation, sequence/version CAS and retained replay outcome. |
| Supervisor command | At the installation gate, stable `(installation generation, command ID)` with digest, `I`, accepted/revoked/started/stopped state, launch/callback generation and final proof. Persisted across supervisor restart. Same ID/digest joins the existing command; changed digest conflicts. |
| Released tombstone | Original identity/digests, final version/sequence, command ID, recovery generation, proof/disposition, event and replay receipt identity. It rejects late evidence/publication and conflicting duplicate create forever within that installation generation. |

States are `armed` (durably committed, launch not yet established), `dispatched` (command admission/dispatch recorded), `unresolved` (authority ended or outcome uncertain), and `released` (verified final reconciliation). These are internal custody states, not additions to public task or bridge enums. Every armed/dispatched/unresolved record owns an installation hold. Unknown or corrupt custody is a hold, not absence. A terminal task can coexist with unresolved custody; its status never grants reuse.

`lost_quarantined` is an explicit terminal recovery disposition with `stop_confirmed=false` and a retained quarantine hold. It can close bookkeeping and revoke old credentials without asserting stop. It cannot free the original installation, authorize task retry there or be mistaken for `released`. Only later independent repair/fencing can retire that quarantine, or an explicitly selected isolated replacement can accept new work. A recorded failure/cancellation and a recorded stop are different facts.

Normal transitions are `absent → armed → dispatched → released`; uncertainty moves any held state to `unresolved`. A never-dispatched proof can reconcile `armed → released`. Recovery can move held states to `lost_quarantined`, then to a documented repaired disposition with independent fence evidence. No state or receipt regresses; a released tombstone is immutable. A later repair adds a new linked audit record rather than rewriting `stop_confirmed=false` history. Complete binding means the Runtime-owned fields of `I`; it does not require an external target or producer manifest. For local work without an external binding row, create must insert/validate the corresponding local attempt/install binding in the same transaction, never skip custody.

## 4. Universal admission and release invariant (B1)

For any held custody, no claim, execution resume, retry, attempt reset, competing install or release of its reservations is allowed until §§5–7 validate closure. This predicate is checked under the same transaction as each granting or releasing mutation. It uses durable custody/installation ownership, never just `task.status`, target verification, manifest existence, lease expiry or current executor ID. A migration/startup integrity check refuses missing custody-to-hold/reservation links; it never repairs a gap by allowing work.

| Integration point / bypass | Mandatory behavior while held |
|---|---|
| Runtime restart (`store.py:1312–1385`) | Advance the Runtime epoch and revoke old ordinary execution/publication, but retain `I`, attempts, pending publication and reservations. Do not reset/requeue into execution. Do not refresh a held prepared binding into new execution authority. Expose recovery-needed hold facts even if public status is queued/failed/cancelled. |
| Claims / task submission / delegated claims | Check both the original attempt hold and installation scope across all task/executor identities and aliases. No semantic reuse, new idempotency key, replacement executor or child can bypass it. Read-only inspect is permitted. |
| Task retry and run retry (`retry_run` and task retry service path) | Check before clearing result, releasing reservations or resetting identity. A run retry selecting any held child refuses the selected mutation atomically and returns the exact blocking custody; it cannot silently retry it or partially clear its holds. |
| Checkpoint resume into execution | Check before issuing a successor attempt/fence. Recovery can inspect old checkpoints, but may not revive their launch/publication authority. Only a released disposition permits separately admitted fresh execution. |
| `reset_execution_attempt`, release helpers, maintenance/clear/purge | Guard low-level helpers as well as callers. Refuse deletion/reset/compaction of unresolved identity, reservations, receipts or pinned bytes. A foreign-key failure is not a cleanup instruction. |
| Reaper, lease/deadline/attempt-limit failure (`3798–3869`) | Expiry and hard bounds revoke ordinary authority; they are not stop proof. Preserve holds even when failure is recorded. No deadline, malformed deadline, terminal status or maximum-attempt shortcut releases custody. |
| Task cancel, owner unbound cancel and run cancel (`6224–6400`) | Record intent and fence launch/publication; retain exact task/attempt/binding and holds. Include local/no-target/no-manifest rows. A caller-supplied `stop_observed=True` never authorizes release. A run's terminal state does not discharge children. |
| Failure (`6461–6489`), success/settlement and output publication | Record truthful execution/publication facts as permitted; do not release custody on an unverified terminal report. Final custody release requires the verified closure transaction. Keep pending journal/publication identity, result bytes and actual installer outcome on failure as well as success. |
| Resource admission / new installation owner (`4136`) | Keep ordinary reservations and add installation-wide exclusion. Executor-scoped `(executor_id, resource_key)` is insufficient. A replacement incarnation sees the old hold. Unrelated installations remain available. |
| Restore, rollback and old-binary start | Treat unresolved snapshot custody and unknown post-snapshot work as held; reconcile current supervisor reality before admission (§9). An old binary that cannot enforce holds cannot start against that installation. |

The Agent `generic_host.py:10829–10840` correction is a separate mandatory enablement dependency: local cleanup alone leaves stop unobserved, retains the uncertainty latch and reports `cancel_requested`/`provider_state_unknown` as appropriate. Even after that fix, Runtime must reject the bare boolean as release authority. Absence of a producer manifest or verified external target never weakens this rule.

## 5. Transaction boundaries, dispatch and publication (B2/B4)

**Create.** Before the transaction, validate request shape and stage any immutable referenced bytes into quota-controlled storage: write, hash, fsync file and containing directory, then pin against collection. Inside one serialized write transaction (`BEGIN IMMEDIATE` or equivalent), validate current epoch, unexpired lease/deadline, exact complete attempt/binding, enrolled installation ownership, all required unreleased reservations and capacity. Insert custody, bind the existing reservations, acquire installation exclusion and commit the create event plus exact idempotency receipt together. Enforce unique attempt and active installation identity in the database. No ACK or positive readback precedes durable commit. A staging/commit failure dispatches nothing; orphan staging is collected only after proving no committed reference.

An exact duplicate create compares the immutable canonical request digest, resolves to the same custody/receipt and produces no event, reservation or command duplication. Changed bytes with the same key, a new key for the same held attempt, or an already-held installation conflict. After closure an exact replay returns the tombstone; it cannot arm again. Readback unavailability means no launch. Create ACK/readback is evidence of custody, not a reusable launch permit.

**Dispatch.** Under a new CAS transaction, recheck the live original lease, epoch and custody version, then persist one command ID/digest and the launch-gate generation in custody, plus dispatch intent/event/receipt, before contacting H2. Issue a separate single-use launch authorization, scoped to that command/digest/installation/generation and expiring no later than the original lease; it is private transport authority, never a create receipt or public reference. Cancellation and recovery durably revoke its generation. Out of transaction, submit that exact command through the authenticated installation gate. H2 durably registers/deduplicates it before any installer side effect and checks installation ownership and generation. At actual launch admission it verifies current Runtime authority through the enrolled channel; expired, revoked, stale-epoch or unavailable authority refuses launch. A cancellation racing an already-admitted launch retains the hold until H2 closes and proves that command stopped. Retransmission/query joins the same command, including when launch ACK was lost. There is no replacement command, new installer invocation or direct spawn fallback on uncertainty.

At H2, registration, generation closure and launch admission serialize. Recovery first closes the old launch generation durably: subsequent registrations, delayed permits, callbacks and writes for it are rejected. Each delayed launch/callback must also pass the current-authority check when entering its gate; an offline cached permit cannot initiate work after Runtime revocation. If launch already crossed the gate, recovery must stop/fence that command and every descendant/write path before producing closure evidence. If it never crossed, the persisted revoked command/generation and complete admission log can prove never-dispatched. A missing command, missing ACK or an idle PID alone cannot. H2 storage loss or a restarted H2 without the old ledger fails closed into repair. Direct workers have no alternate installer/write authority outside this gate; if such authority exists, tracked enablement is forbidden.

Every external H2/query/stop/repair call happens outside a DB transaction. On return Runtime opens a short transaction and revalidates identity, expected custody version, current recovery/launch generation, trust-key revocation and installation hold before applying the result. If anything changed, the result is stale; read/verify again with a new CAS request. No lock held across network/process calls can supply the missing distributed fence: H2's durable gate closure supplies it.

**Checkpoints/evidence.** A request includes immutable request digest, stable mutation key, expected custody version, sequence `last+1`, `I` and references. Stage and pin durable bytes first. One CAS transaction commits the checkpoint, reference ownership, incremented version/sequence, event and exact replay receipt. Exact key/digest replay returns the stored result even if its original expected version is now old; a changed digest conflicts. An old/duplicate sequence under another key, gaps, stale version, wrong epoch/attempt or released tombstone cannot mutate. Recovery evidence uses the separate recovery authority, never an expired normal lease. Late normal checkpoint/terminal callbacks are fenced after loss/closure.

**Final reconciliation.** Stage authenticated proof and referenced publication/journal bytes; verify content, identity, gate closure and actual outcome outside the transaction. Then, in a single CAS transaction, revalidate everything above and atomically store proof/disposition, truthful task and attempt terminal state, binding state, reservation disposition, installation hold disposition, audit event and exact replay receipt. Release reservations only for verified stop or never-dispatched closure and verified absence of remaining write authority. For lost disposition transfer their exclusion into quarantine atomically, rather than creating a free interval. Existing confirmed task outcomes are preserved; pending/unknown outcomes are not synthesized into success. Any still-missing publication/journal linkage remains recovery-needed even if process custody is closed.

A crash yields either all retained state or all final state, never a partially released installation. Reconciliation replay after a lost response returns the same durable result/event IDs without extra releases/events/dispatch. Released records reject all late conflicting writes; recovery cannot issue installer work. Evidence pins last through reconciliation and retention (§7). A mutable path without pinned exact bytes is not acceptable pending publication evidence.

Disposition mapping is explicit: never-dispatched closure records no installer execution and terminalizes the task as cancelled if cancellation was requested, otherwise failed with a never-dispatched reason. Verified stopped closure preserves an existing validated terminal result; if outcome/journal evidence is incomplete, it records a failed task with outcome-unknown diagnostics and leaves the update job/journal recovery-needed. Lost disposition records task cancellation/failure according to the original intent, attempt bookkeeping closed with a lost marker, binding lost and reservations quarantined, always with `stop_confirmed=false`. None of these paths overwrites already confirmed install success/rollback/failure or fabricates a job/journal result from task status. The transaction records both the execution facts and separate custody disposition.

## 6. Trusted proof producer and recovery authority (B3)

**Producer.** H2 means the privileged installation supervisor/admission gate in the selected Agent installer boundary, outside the task worker and its cleanup finalizers. This is a required new implementation contract, not a claim that current `astrid/installer/custody.py` supplies it. H2 owns the durable command ledger and the ability to close launch, child, pending callback, publication and filesystem write authority for the enrolled installation. Runtime's proposed custody verifier is the only consumer that can turn H2 evidence into a DB release. Host reports, task output and local cleanup are untrusted observations for this purpose.

**Enrollment and keys.** Owner/admin enrollment, authenticated independently of task leases, binds installation/realm roots, supervisor service identity, platform birth identity and an Ed25519 verification key ID to a trust version. H2 keeps its private key in the OS-protected installation service credential store, never in task environment, arguments, public references, receipt or show/follow output. Runtime stores the enrolled public key/trust record under owner-only mutation. Authenticated local IPC or mutually authenticated transport limits H2 calls to the Runtime recovery role and enrolled scope. A public recovery reference or proof digest is an identifier, never a credential.

Key rotation requires owner/admin approval plus continuity signed by the previous key, or the loss/repair route below; it increments trust version. Revocation is immediate at verification and commit, invalidates uncommitted proofs/requests and closes old command authority. Already-committed verified history remains history. A new key or supervisor birth does not retrospectively prove the previous supervisor stopped. Lost-key recovery must independently fence old authority before the new enrollment can authorize reuse. Duplicate/unrecognized key IDs and unknown proof versions refuse release.

**Proof format.** Proposed `astrid-install-custody-proof/v1` uses strict canonical JSON, SHA-256 digests (`sha256:` plus 64 lowercase hex), and an Ed25519 signature over the domain-separated canonical bytes. The signed body includes key/trust version, proof ID, Runtime challenge nonce, current recovery generation and expected custody version, custody ID and all of `I`, command ID/digest, old launch/callback generation and durable closed-generation watermark, supervisor service/boot/process birth identity, evidence digests/lengths, exact child/write-scope coverage, pending callbacks/queues and their disposition, observed installer outcome and journal/publication linkage, and disposition (`stopped` or `never_dispatched`). Unknown/missing fields required for scope closure fail verification; a signature alone does not prove scope coverage.

Birth identity includes machine/boot identity and immutable OS process creation identity (Linux boot UUID plus start ticks; the equivalent Windows/macOS birth identity), not PID alone. Proof says every old command, child, queued/delayed callback, delegated writer and handle capable of modifying the installation is stopped or independently fenced, and that its closed gate cannot authorize more work. Observing an idle or absent leader is insufficient. A proof must remain reproducible from H2's durable ledger after process exit. Runtime verifies signature, current trust/revocation, nonce, exact realm/install/attempt/incarnation/epoch binding, expected version/generation, command closure and all reference bytes. Partial census, unknown descendants or loss of fence durability returns unresolved.

**Separate recovery operation.** Proposed CLI syntax below describes a new Runtime task control operation; none of these commands is claimed to exist today. Its wire schema and generated clients require separately assigned Runtime work. It does not extend `POST /v1/update`.

```text
astrid-tools tasks custody inspect <task-id> --json
astrid-tools tasks custody reconcile <task-id> --custody <id> --expected-version <v> \
  --recovery-generation <g> --identity-file <original-public-binding> --idempotency-key <key>
astrid-tools tasks custody repair <task-id> --custody <id> --expected-version <v> \
  --recovery-generation <g> --disposition lost --reason <reason> --idempotency-key <key>
```

Inspect/show/follow is read-only and returns redacted `I`, custody version, hold reason, safe references, proof/dispatch status, storage usage and the exact next action. Reconcile requires authenticated realm owner with admin scope, exact old `I`, expected custody version, stable request key/digest and a **current recovery generation** separate from the original Runtime epoch/lease. Runtime allocates that generation and a nonce in a durable CAS operation under current owner authority; the client receives public IDs, not a new normal execution credential. Retries query/reconcile the same command. A second owner call conflicts or joins by exact key; it cannot take over an in-flight generation silently. After timeout or restart a new owner-authorized CAS may supersede the generation, fencing earlier responses. No old lease is renewed to collect evidence, launch work or publish a replacement result.

The user path is inspect → authenticated reconcile → either verified closure or typed unresolved with a repair instruction → authenticated lost/quarantine and repair or isolated replacement. Existing owner/admin `abandon_task` cannot be reused as this exit: its `_abandon_external_attempt` requires verified external placement and excludes the local executor. This protocol explicitly covers local workers without a manifest/target.

**Loss and repair exit.** Owner/admin can record `lost_quarantined` without H2 proof, using exact identity/version/generation and an auditable reason. Runtime durably revokes the old launch/callback generation, all normal credentials and delayed Runtime publication; the required current-authority admission check rejects delayed launch/callback requests even when the old H2 cannot acknowledge revocation. Already-admitted native writes remain possible until independent stop/fencing, so Runtime records `stop_confirmed=false`, preserves actual known outcome/pending bytes and retains the physical installation quarantine. It does not claim remote stop, billing stop, successful update or released storage. This gives an honest terminal disposition and a supported repair path without editing SQLite.

For reuse, an independent OS/installation repair authority, enrolled by owner/admin outside the lost worker/key, must close autostart and launch sources, stop and verify all old service/process incarnations, revoke old credentials/handles/mount access and drain or permanently fence all delayed callback/write paths. It signs a scoped repair receipt binding the old installation/generation and the new exclusive gate. Merely rotating a key or moving a directory cannot fence an open writer. If absence/revocation cannot be established, the original installation remains quarantined indefinitely. The supported alternative is an isolated replacement: a new installation generation with separate program/data roots and access controls denying every old principal write access; verified data may be copied from a read-only snapshot, never shared writable roots. Owner/admin explicitly selects it in a new operation linked to the lost disposition. Relabeling the same roots/UUID is rejected. Retrying the old held task is not a replacement procedure.

## 7. Bounds, retention and actionable uncertainty (B3)

Each reconcile invocation has an absolute **30 second** server deadline, including lock wait, H2 calls, validation and commit. External calls get at most 10 seconds each and consume the remaining budget; Runtime must cancel/stop waiting by the deadline. At most two H2 attempts occur in one invocation, with 250 ms backoff. Failure returns typed `unresolved` with `hold_reason`, exact custody/version/generation, retryability, `retry_after_seconds` and next inspect/repair action. DB busy, proof invalid, fence unknown, supervisor unavailable and quota exhausted are distinct reasons. A commit whose result cannot be confirmed by the response deadline returns `commit_outcome_unknown` with the exact request key and a readback instruction; never claim rollback or success from a timeout. A bounded request dispatcher must stop waiting even if storage completion remains pending; durable CAS/receipts still decide the eventual outcome. Timeout never releases anything and does not bound how long reality may remain uncertain.

Across invocations an optional client poll backs off 1, 2, 4, 8, 16, then 30 seconds and stops after five invocations to present inspect/repair; it does not background-loop forever. Stale generation/version returns conflict and current redacted state. Lost response is handled by key receipt/readback, not a new mutation. A supervisor operation still running after client timeout remains subject to its generation fence; its late reply cannot mutate a newer generation.

| Bound | Proposed mandatory limit and failure behavior |
|---|---|
| Custody/proof/control metadata | 64 KiB canonical UTF-8 per request, response or stored metadata body, including the signed proof envelope. Reject oversized data before mutation; paginate inspect/follow. |
| Opaque references / digests | References at most 128 bytes, no credentials or arbitrary remote URLs; SHA-256 encoding fixed as above. Resolve only through authenticated enrolled stores; validate declared and actual length/digest. |
| References / update count | At most 32 evidence references per checkpoint/reconcile update, 256 pinned references total per custody, and 1,024 checkpoint/evidence mutations per custody. Exact duplicate replay consumes none. More detail uses one immutable bounded manifest, within the same byte quota. |
| Durable storage | Default admission budget 64 MiB per custody, 1 GiB per realm, and 1,024 held custody records per realm, charged across metadata, blobs, receipts and supervisor ledger. Reserve 1 MiB control/recovery space per admitted custody before dispatch, with room for final reconciliation and lost-plus-repair audit/receipts that normal updates or repeated recovery intents cannot consume. Reject new work before arming if capacity or disk reserve cannot be guaranteed; independent OS quota checks must agree. |
| Recovery after exhaustion | Normal updates stop before consuming the reserved recovery space; bounded reconciliation/lost/repair receipts use it. If actual storage fails, return `storage_unavailable` and keep the hold; restore writable capacity through the supported offline backup/repair operation, preserving all held bytes, then retry. No success ACK without durable recording. |

Large logs/outputs go into immutable quota-controlled storage; a digest/path does not excuse unbounded fetch or retention. H2 must reserve command/proof space before accepting dispatch and must refuse rather than execute without a durable ledger. Limits may be configured downward before admission; raising them is an owner/admin capacity action and cannot change security semantics. New admissions stop when retained tombstones exhaust the allocated budget; unresolved records/evidence are never evicted to make room.

Unresolved and quarantine records, their exact pending publication bytes and evidence/receipts are pinned indefinitely. A pending publication/journal remains pinned even after process custody closes, until its separate reconciliation or explicit authenticated lost-publication disposition; the custody retention clock cannot delete it. After verified closure, retain full evidence and exact replay result bodies for at least 30 days **and** until owner acknowledgement of a verified replacement backup, whichever is later. Compaction then retains immutable identity/digest/disposition/event/command/version tombstones and an exact replay outcome or digest-bound archived receipt. An expired body returns typed receipt-archived with a safe retrieval action; it never reruns a mutation. No key reuse after compaction. H2 retains dedup/revocation tombstones at least as long as Runtime can accept an old command; retirement of an entire installation generation requires independent permanent fencing and an archive before compaction. GC and backup verify pins/reference closure before removing anything.

## 8. Complete crash and race protocol (B4)

Each row is a mandatory fault-injection case. Repeat with **two successive Runtime restarts**, H2 restart where relevant, concurrent owner cancellation and competing reconciliation. Persistent truth and installer invocation count, not just displayed status, are the oracle.

| Boundary | Durable state / only permissible recovery |
|---|---|
| (a) Before or during create commit | No installer side effect. Rollback leaves no custody; committed custody is discoverable by exact create identity/receipt. Unavailable readback cannot authorize dispatch. Staged orphan bytes are harmless and never substitute for a committed record. |
| (b) After commit before ACK/readback; after readback before dispatch | Armed custody/holds remain. Duplicate create returns the same receipt, not another launch right. Close never-dispatched only after H2 closes every old generation/permit and supplies authoritative non-dispatch evidence. An unavailable supervisor keeps the hold. |
| (c) While registering/dispatching; launch ACK lost | Runtime intent/command ID already exists. H2 durable dedup admits at most one command. Query/resubmit that ID; never create a replacement or infer absence. Before native spawn H2 durably marks the command `launching`; after a crash that marker prohibits another spawn until independent evidence proves non-dispatch and fences delayed launch. A definitely never-admitted command may be revoked or admitted once under still-current authority; an ambiguous launch remains unresolved and is contained/reconciled, never blindly resumed. Delayed registration racing recovery is rejected by the closed generation or joined as already launched and contained. |
| (d) During work/checkpoint/pending publication; host death, lease/deadline expiry, restart, cancellation | Fence ordinary execution/publication and old launch generation; retain original identity/holds and exact pending result/journal bytes. No new task/executor/attempt or checkpoint resume runs against the installation. Checkpoint crash commits all refs/sequence/event/receipt or none. |
| (e) Actual stop/completion before durable proof | Stay unresolved. H2 reproduces its signed closure from its durable ledger, binding the current recovery challenge; otherwise inspect → authenticated lost/quarantine → independent repair/replacement. Cleanup, absent manifest, task failure and a stop boolean do not prove closure. Preserve observed actual installer outcome separately. |
| (f) Proof staged/verified before or during release commit | Staging releases nothing. Revalidate trust, identity/version/generation and pinned bytes, then retry exact reconciliation. DB rollback retains all holds; committed transaction contains complete disposition/task/attempt/binding/reservation/event/receipt state. No external stop call occurs inside this transaction. |
| (g) Release committed before reply/readback | Exact replay returns the committed disposition and event IDs. No new event, release or dispatch. Tombstones reject late checkpoint/terminal callbacks. Actual install outcome and pending journal/publication linkage remain truthful; missing linkage stays recovery-needed rather than becoming synthetic completion. |

A Runtime restart changes current recovery authority, never the original execution epoch. H2 closure must survive both restarts and precede release. If H2 loses its closure/dedup store, restoration from an old snapshot is not authority to accept commands; independent repair or quarantine is required. Concurrency between cancel, proof verification, key revocation and final commit is resolved by version/generation CAS and commit-time trust checks; losers return the winner's receipt or a typed conflict, without side effects.

## 9. Versioned schema migration, backup, restore and rollback (B5)

The reviewed candidate declares `SCHEMA_VERSION=33`. `v33_manifest.py` classifies the exact U33 inventory with fingerprint `6ed4d1f145aa5fd8d9691b8b7d072f4e176ad857d4dda586f72b4a64c0e09ff3`. `upgrade.py:1008–1027` treats completed current v33 as already migrated. Adding custody tables under identity 33 would break that classifier and is forbidden.

Require **U33 → U34**, normally schema version 34, in separately assigned Runtime implementation. If M-INT allocates 34 elsewhere, assign the next version explicitly and revise this packet; do not silently reuse 33 or accept arbitrary additive layouts. Before that implementation is approved, its migration receipt must pin the actual published round1b U33 source fingerprint and the exact target fingerprint generated from final SQL, indexes, checks and foreign keys. The target hash cannot truthfully be supplied before that SQL exists. Fresh U34 and migrated U34 must have identical canonical manifests. A source delta from the fingerprint above requires reclassification/review, not widening the allowlist to unknown layouts.

The coordinated Runtime change includes schema version/declaration, classifier and zero-write admission, offline upgrader, custody/hold/receipt constraints and indexes, integrity and reference checks, backup/restore inventories and CAS pinning, lifecycle/owner fences, CLI/API schemas, generated contracts and compatibility tests. M-AG later vendors only an M-INT-published integration producer; this design does no generation or pin selection.

Migration protocol:

1. Preflight read-only using detached WAL-consistent observation. Accept only the pinned completed U33 source. Unknown/newer/hybrid/damaged layouts refuse with zero writes, signals, sidecars or lock-marker changes. Do not infer U33 from the integer version alone.
2. If v33 activation/backfill is pending, finish it through the existing v33 classifier/frozen plan/provider-readiness protocol or perform its explicit operator recovery first. Interrupted restoration remains offline. Never reinterpret `schema_committed`, `plan_persisted`, `backfill_committed` or another pending activation as custody-ready, modify the old recovery archive, rerun backfill against changed witnesses or mint new media pins prematurely.
3. Stop admission and acquire writer/realm-owner and installation exclusion. Inventory possible legacy in-flight installers before any startup reconciliation can requeue them. If their absence cannot be independently established, create explicit quarantine holds with preserved legacy identities and `stop_confirmed=false`; these are not fabricated historical custody or evidence. If that inventory cannot be safely bounded/captured, refuse activation and require operator repair. No automatic installer dispatch during migration.
4. Before mutation, produce and verify a new, WAL-consistent **full recovery set** (realm DB and sidecars as needed, CAS/evidence, data/outbox/publication bytes, replay receipts, hold inventory, installation/supervisor ledger linkage, owner/lifecycle records and digests). Fsync bytes and archive/activation markers. Retain the separate v33 archive and a chain to it. Backup/capacity/verification failure leaves original data intact and migration offline; never overwrite the only recovery set.
5. Under exclusion, reclassify schema, realm and file identity and verify unchanged scope. In one DB transaction apply DDL, constraints/indexes, explicit quarantine inventory if needed, migration event/receipt and target version. Verify target manifest plus integrity/foreign keys/reference closure before commit and again on a detached committed image. Existing task/attempt/event/result bytes and evidence references remain unchanged; only new migration/quarantine audit data is added. Preserve original journal identity. Commit durably, then advance the separate migration activation record.
6. Before marking custody-ready, verify the target image, recovery set, supervisor enrollment/fences, quarantine coverage and provider/lifecycle readiness. Startup/restart checks activation before task recovery. A new schema is not permission to enable tracked installs: the route stays disabled until §12's gates pass.

Interrupted migration has explicit outcomes: before archive verification, no DB mutation; before DDL commit, rollback to exact U33 with archive retained; after DDL commit but before activation marker, identify exact U34 and the pending operation, verify and resume that operation rather than reapply DDL; during activation/restore, refuse service admission until explicit offline recover completes. Contradictory markers/fingerprints return actionable offline recovery, never online repair. Old binaries must reject U34 before mutation; prove this with the actual previous executable.

Backup/restore must include unresolved and quarantined custody, reservations/installation holds, immutable evidence, command/replay receipts and their integrity/pin inventory. A restored DB cannot roll back the supervisor ledger. Restore into an inactive realm; acquire independent installation exclusion, verify the full set, start with a new Runtime epoch and recovery generation, compare with current H2 command/generation reality and quarantine any post-snapshot or unknown commands before ordinary admission. A snapshot is never stop proof. Missing evidence, stale credentials or unavailable H2 leaves inspect/recovery available and execution held.

Rollback may not erase custody then let an older Runtime requeue surviving work. Automatic full-set rollback is confined to the independently fenced pre-admission window and must restore/verify the complete matching set before the actual old executable starts, preserving documented v33 full-set guarantees. Once U34 admits writes/work, retain a verified current full set and all post-upgrade user data; no destructive automatic downgrade. Starting old code requires independently proven quiescence of all old and new commands/callbacks plus permanent revocation of delayed authority, or an external exclusion gate understood and enforced before old code can start. If the old executable cannot honor that gate, it must not start. Offer offline inspect/export/repair or isolated replacement; never discard post-upgrade data to make rollback appear successful. A new-epoch restore still reconciles live supervisor reality before any task retry.

requested operation ID = job.operation_id = journal.update_job.operation_id
