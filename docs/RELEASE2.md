# Release 2: resident starter and apply-at-launch

**Status: specification and plan, not evidence of implementation or release.** Release 2 delivers the resident starter through the Release 1 bridge, adopts existing installations, and consolidates updates around staging a complete version and applying it at launch. The product outcome is quiet background staging, a clear restart choice, and recovery that preserves users' work across direct and Pinokio installations on macOS, Linux and Windows.

This document consolidates the Release 2 direction in `lifecycle/PLAN.md`, particularly §§1–2 and phase D, with the compatibility and qualification obligations in `lifecycle/END-STATE.md`, `lifecycle/LAUNCH.md`, and the Release 1 bridge contract in the handoff. PLAN §§1–2 supersede END-STATE's older end-state description. Release 1 execution remains governed by `lifecycle/release-1/START-HERE.md` and `lifecycle/RELEASE1-TASKS.md`. Where a contract remains unsettled, this specification does not supply missing wire details or claim sign-off.

## User-facing result

- A complete update stages while Astrid is running. The user sees that it is ready and can restart after current work finishes. New work is held while draining. An explicit “now” choice interrupts work with consent and explains that it may need retry; it does not promise automatic retry until settlement is proven.
- On the next start, the candidate is checked and any necessary data migration is completed before Astrid accepts work. If a pre-commit update fails, Astrid restores the previous version and applicable data snapshot, reports the outcome, and offers Retry and Copy diagnostics. Retry makes the suppressed candidate eligible again. Drafts are protected before restart.
- Install, update and repair converge on the same lifecycle path; rerunning the install line remains the supported repair. Status exposes understandable stages and a durable outcome. Pinokio retains its own Start, Update and Open surfaces, with Open gated on readiness.
- Existing direct and Pinokio users keep their data and can update whether they are on Release 1 or skipped it from Release 0. The plan recommends the hosted editor as the default; fully local remains a supported choice. The final default should be confirmed against the latest release decision.

## How it works

A release is staged as a complete immutable `versions/<id>/` directory, made visible atomically; program versions and user data live separately. The newest eligible staged version is pending. A stable `<root>/run` starter, using a pinned interpreter independent of release code, is the supervisor entry point. It holds the stable `run.lock`, contains and waits for the Runtime process tree, and hands write authority to the selected release rather than requiring the child to reacquire its lifetime lock. External engines are outside this boundary and are reconciled, not killed.

The starter selects the newest eligible, non-suppressed staged version newer than current, otherwise current. It starts that version's `start-release`. Stop intent takes precedence over a concurrent restart; exit 75 asks the starter to loop for an update, while ordinary stop exits cleanly. A candidate gets one attempt: failure before commit suppresses it and returns to the previous version once; if that also fails, stop and surface diagnostics. There must be a fallback even when candidate code cannot start. The entry contract specifies ownership transfer, exit and stop semantics, interpreter home, transaction compatibility, atomic starter upgrade, and recovery transitions, including missing or corrupt state.

For a transition, `start-release` records trial/current/previous state. Runtime retains its owner fence and recovers an unfinished transition before opening: snapshot realm and relevant support state, migrate, run the maintenance/self-check with mutations and task execution closed, then commit and admit work. Clear the trial and record the outcome after commit. Snapshots are for transitions, not ordinary restarts. A committed transition is final: recovery must not silently restore old data over subsequently admitted work. Staging leftovers are ignored and cleaned only after their writer is gone. Cleanup retains current, previous, staged and in-use versions, including a launcher's interpreter.

The intended compact install state includes roots, supervisor, current/previous/trial, suppressed candidates, last outcome, stop and uninstall intent; only the owner of the stable lock writes it, with write rights passed to the release. Use compare-and-set and durable ordering where state changes require them. Runtime continues to own its store, snapshots and fences; OS units own autostart settings, which must survive updates. Uninstall is resumable, keeps user data by default, and never removes external engines.

## Scope and compatibility

1. **Starter and apply:** implement the loop, exit-75 handoff, stop intent, process containment (a non-inherited Windows Job and POSIX parent-death guard/watchdog), pinned interpreter, `start-release`, fallback and Retry. Reuse existing locking and process primitives where they fit. Units and supported supervisors point to `run`.
2. **One adoption:** migrate Release 0 and Release 1 roots directly into the final layout, preserving roots, ownership, service identity, settings and data. Recognize authentic Release 0 service/install provenance; do not strand users who skip Release 1. Maintain readers for pending legacy workers and records, including Release 1 app, job and applicable local journals, until safely resolved. Retain old code and inputs while an old worker needs them.
3. **Frozen bridge:** the unchanged Release 1 worker must be able to invoke and observe Release 2 via the shipped install URLs and v1 manifest envelope, Node pin, `--manifest --root --data-root --update-job`, job and journal results, `POST /v1/update` and status, Pinokio stop handshake and installer-lock handoff. Preserve the old worker's completion and cleanup; the resident starter must not deadlock it. Consult the bridge contract for exact settled behavior and fixtures. Its current draft identifies unresolved stop-wire and final Release 2 tuple/result details; resolve those through the contract before claiming compatibility.
4. **Pinokio and old callers:** migrate Release 0/1 Pinokio installations so Pinokio supervises `run` and calls the common lifecycle commands. Retire the special adapter only after migration and compatibility are proven. Preserve legacy `--update-app` and `--update-job` entry points as compatible aliases; their old callers and in-flight operations still need their documented results.
5. **Update experience:** reuse Settings surfaces for stage-ready state, drain/interrupt choice, status stages, Retry and Copy diagnostics. Preserve draft-safe behavior and truthful failure and recovery messages. A beta channel is a second manifest URL.
6. **Consolidation:** after replacement and migration are proven, remove transient OS update jobs and `app_update`, rebase tests, and collapse redundant records in the adoption rather than performing a second layout migration. Change the mypy ratchet from counts to diagnostic identities.

## Dependencies and sequencing

- **Release 1 bridge:** freeze and qualify the bridge against the actual Release 1 worker before relying on it. A stand-in Release 2 rehearsal demonstrates reachability, not the real Release 2 starter or release qualification.
- **Runtime snapshot (PLAN phase F):** a durable, idempotent snapshot/apply/revert/commit capability covering realm and support state, with recovery information durable before destructive work, is required for the planned Runtime-owned rollback. Keep the installer backup and restore path until the replacement passes; do not remove it merely because the starter exists. Before any release that changes workspace schema, close mutations until commit and address restore completion, durable backup/restore and power-loss verification.
- **Release artifacts and local editor (phases H + I):** the broader plan builds a tuple-pinned, hashed and signed release from CI artifacts, verified before candidate code runs; the local editor and renderer assets ship as artifacts, with Runtime serving the editor on loopback. Carry real user state across the origin change. Remove local source-clone/build/update paths only once the bundle migration works; keep developer `dev:local`. Editor compatibility uses release floor and capabilities with an update-only fallback, preserving old clients and drafts. These are adjacent planned slices, not evidence that they already ship.
- **Settlement:** retain drain admission for Release 2. Offer a stronger retry promise only after per-attempt reconciliation, external request identity, duplicate suppression and ambiguous outcomes are proven during normal operation and after restart.
- **Launcher entry contract:** settle its state-transition and ownership rules before implementing against them. Respect the Release 1 bridge rather than changing its old-reader assumptions.

## Release acceptance

The following is a proposed acceptance checklist derived from the plan and supporting contracts; confirm it against the final Release 2 decisions. Qualification uses the actual pinned Release 2 tuple and authentic old installations, not a release-number-only stand-in. Retain machine-readable receipts identifying inputs, target, platform, mode, scenario and outcome; missing or skipped required evidence fails the release gate.

- On macOS, Linux and Windows, exercise real Release 1 → Release 2 via supported shipped entry points, including the direct install line and in-app update where supported, and Pinokio Update for managed modes. Exercise authentic Release 0 → Release 2 directly, including direct and Pinokio adoption, with no intermediate Release 1 mutation. Verify service and installation identity, selected version, terminal result, preserved separate data root and usable work.
- Exercise fresh installation, interrupted transactions and recovery, candidate failure and rollback to the actual previous executable and data, subsequent Retry, and keep-data uninstall. Inject failures around staging, handoff, switching, migration and commit; verify safe recovery or refusal, no unintended work admission, and no restore after commit. Test schema-changing migration and power-loss durability before one is shipped.
- Test each applicable supervisor's start, stop, restart and containment behavior: launchd and systemd consume restart internally and forward stop; Windows Task Scheduler uses a contained hidden launcher and stop mechanism; Pinokio Stop works while its shell owns the launcher; terminal Ctrl+C stops without applying; container operation handles PID 1 or an init. Stop intent wins over restart. Verify children do not survive unexpectedly and external engines are not killed.
- Verify frozen bridge fixtures against the unchanged Release 1 worker, including old job/journal recovery, lost acknowledgement, lock and stop refusal, completion and cleanup; test legacy callers and retain old code until no longer in use. A free-lock observation alone is not ownership.
- Exercise drain and explicit interruption messaging, draft preservation, status and durable failed-update recovery, Retry and diagnostics; preserve autostart choice and ensure Pinokio Open waits for readiness. Qualify local-mode migration and editor compatibility when those planned slices are included.
- Run launcher/transition fault tests and lifecycle lanes on the relevant tuple, enforce no new mypy diagnostics by identity, and link release receipts. Existing synthetic or same-version harness results are useful building blocks, not proof of the real transition.

## Boundaries and planning

Phase D was estimated in PLAN at **31–44 experienced-engineer days**, including starter, apply, adoption, Pinokio migration, UX, beta URL, supervisor acceptance and real three-OS rehearsal, and deletion/rebased tests. This is an estimate, not a commitment or evidence of completed work; snapshot and release-artifact slices are separately estimated dependencies. Reuse existing journey drivers and fixtures without treating their current coverage as Release 2 qualification.

Automatic outcome and crash uploads, staged rollout, managed engines and pods, a Windows `.exe`, and a possible desktop shell are deferred. A desktop shell remains an owner decision after Release 2 based on need. The external-engine and task-settlement improvements in PLAN phase C are adjacent work; they do not justify claiming full crash-only task recovery before it is proven.
