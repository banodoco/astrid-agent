# Staged investigation 2: Worker profile production and Runtime validation

## Conclusion

The pinned product can **consume and validate** a real local Worker profile, but its checked-in production install/session path does not create one. Agent's installer writes an Astrid *source profile* (`profile`, `runtime_checkout`, `source_checkout`, `runtime_environment`, `source_digest`, `service_declaration`); the name and purpose are different from Runtime's optional `worker_profile` path. Pinokio sets `ASTRID_RUNTIME_SOURCE_MANIFEST` to the installed source-profile path and starts `run` or `astrid_runtime`; its session-options parser only accepts `prepareEditor`. No production generator for a machine-specific `worker-profile.json` was found in the pinned Agent or Pinokio source. Runtime has the `--worker-profile` consumption route, but that is not a profile-construction command.

This checkout cannot demonstrate an engine-backed Worker start on Linux through the explicit relay path because its custody broker rejects Linux before launch (Runtime and Agent both require Darwin audit-token custody). A real target install still supplies live profile values, and profile composition/persistence still needs an owner or installer step. There is Linux VibeComfy engine provisioning: the separate `vibecomfy-h3` RunPod recipe and installed-session path accept target-local placement. Therefore the absent ordinary `vibecomfy` recipe name is not the decisive blocker. No host-only profile can be substituted for Worker+engine proof: host-only avoids Worker/engine/session executables and still uses Runtime's custody-gated relay path on this engine selection.

## Exact fields and real ownership

`runtime/runtime_protocol/local_worker_composition.py:1253-1338` supports two modes and enumerates the top-level allowlist:

- **`worker_engine` (default):** profile ID; target `machine_id`; loopback `engine_endpoint`; `worker_environment`; absolute Worker, host, engine and engine-listener executable paths; each matching artifact SHA-256; session-config SHA-256; `profile_revision`, `profile_digest`, `release_digest`; `source_checkout`, nested `pack_root`; `boot_manifest_path` and `boot_manifest_hash`; optional capability matrix, environment, timeout, engine launch declaration, host OS executable+digest, host protocol. Runtime derives `workspace_uuid`, `realm_root`, and `support_root` from the selected install/runtime owner, not from the profile. `machine_id`, target paths/digests and session config must be obtained from that same real target machine/install. With `engine_launch`, the pinned loader further requires the explicit module/session-root/config/source-revision/source-content-digest/listener-argv/adapter-pins structure and checks the emitted `config.json` digest (`runtime/runtime_protocol/local_execution_supervisor.py:33-38,164-216`).
- **`host_only_cpu`:** it removes Worker, engine and listener roles, but is not an empty/no-op profile. `local_worker_composition.py:1501-1538` still needs machine ID, the currently selected installed Runtime Python as `host_executable`, its host digest, a separately pinned OS/kernel executable and digest, source checkout/pack root, boot manifest and hash, host protocol, `profile_revision`, `profile_digest`, `release_digest`, and a session/config digest equal to the canonical host launch object. `local_execution_supervisor.py:108-163` requires explicit bounded concurrency (1..16), absolute nested paths and a constrained environment. This is a host-only CPU Worker route, not a way to claim the installed VibeComfy engine is ready.

Ownership is split: install/provisioning supplies actual executable trees, their bytes/digests, session/boot/capability files, and machine identity; the Runtime supplies current realm/workspace/support-root binding, Runtime endpoint/instance identity, UID and live process identities during launch; Runtime validates all of these. The selected profile's `profile_digest`/revision are not generated or assigned by current Agent/Pinokio installs.

### Explicit engine-launch adapter is present, but does not generate a profile

This is a distinct path from legacy `worker_engine`: `runtime/runtime_protocol/local_worker_composition.py:492-545` starts the selected Runtime's isolated Python (`sys.executable -X utf8 -I -m runtime_protocol.local_execution_supervisor ...`) after checking `worker_executable` equals the current Runtime kernel executable and its digest. The Runtime supervisor and `agent/astrid/core/execution/generic_host.py` then bind a retained relay/host and use `agent/astrid/core/execution/vibecomfy_engine_adapter.py` to run the selected `vibecomfy.commands.session` module. The adapter requires the exact selected VibeComfy import root, `runtime.session`, `commands.session`, `utils`, observed function pins, plus installed `git` and `ps` helper pins (`vibecomfy_engine_adapter.py:218-288`). The host launch checks the engine/listener executable bytes and adapter source bytes against their pins; verifies the Vibe source revision/content digest and fresh session registry; and uses that real session's `config.json`/`server_argv.json` and observed process/socket identities (`generic_host.py:13840-13879,14028-14099,15753-15829`). It is therefore a real executable integration route available in these pins, not a profile producer or a way to avoid target-machine inputs. Its Python requirement is at least 3.11 (`agent/pyproject.toml:11`; the selected installed runtime still has to be the current Runtime environment).

For the explicit route, the missing producer must bind `engine_launch` to an actual fresh session under the target's `out/sessions/<session>/` tree and source checkout. `source_revision` (40 lowercase hex) and `source_content_digest` (SHA-256) must identify that real VibeComfy checkout; `listener_argv[0]` must be the actual executable pinned as `engine_listener_executable`; the `config` object must produce the exact emitted `config.json` digest; and each adapter seam digest must be computed from the installed pinned adapter/session/spawn/cleanup/stop sources. The resulting Worker profile must also pin the actual relay/Worker interpreter, selected Agent host and engine/listener executable artifacts, release/profile IDs/digests, target machine ID, and Worker/session roots. None of those target install/session values is furnished by the runtime source pin, Agent engine source pin, a recipe/environment lock, or a fixture. A new generator could be implemented to collect them from one real provisioned install, but cannot be truthfully exercised or complete this canary from the inputs available here.

### Decisive Linux platform restriction and boot manifest availability

The explicit relay has a hard Linux custody gate, independent of profile contents or availability of the engine. Runtime calls `RoleBoundCustodyBroker` in `_prepare_relay` at `runtime/runtime_protocol/local_worker_composition.py:492-529`; the constructor rejects any platform except `darwin` or `win32` with `CustodyError("Darwin audit-token custody is unavailable")` at `runtime/astrid_runtime/custody_broker.py:949-970`. On the Agent side, its `RoleBoundCustodyBroker` rejects any platform other than Darwin at `agent/astrid/core/execution/custody_broker.py:1738-1755`. Thus Linux cannot complete the explicit engine-launch custody setup from these pins even if a genuine profile and session tree are provided. This is the decisive in-scope implementation dependency for a Linux runner: add a reviewed Linux custody mechanism on both sides (or perform this engine-backed canary on Darwin). The Runtime and Agent paths must agree on the new OS-backed ownership proof; deleting or bypassing either guard would weaken custody and is not a valid profile fix.

Linux H3 engine provisioning is available and should not be misidentified as the blocker. `agent/astrid/packs/runpod/recipe.linux-cu130.json` pins Linux x86_64/CUDA 13.0, Python 3.12.10, and Vibe source revision `e2905d068d5851b9c32856d32b8251852a01d6dd`; `agent/astrid/packs/runpod/installed_session.py:69-70` invokes `engine_runner.plan_install(recipe, root=root, placement="local")`. Its installed local session path is described at lines 1-4, 69-94, 163 onward. This supports using the Linux engine under a target-local placement; the Linux Runtime/Agent custody gate remains after provisioning. The standard `vibecomfy` package is Windows-recipe-based, but that alone does not establish a Linux inability because the H3 path supplies the Vibe source and local-placement engine.

Boot-manifest composition itself is **not blocked** on undisclosed install data or new code. `agent/astrid/core/gateway/dispatch.py:704-743` exposes `compose_profile_handoff(manifest_path, support_root=...)`, defaulting to the checked-in Vibe registry and frozen conformance records from `agent/astrid/packs/shots/conformance.py:28-80`; it delegates to `stamp_boot_manifest`. Once the selected Agent environment and support root exist, the legitimate invocation is:

```sh
python -c 'from astrid.core.gateway.dispatch import compose_profile_handoff; compose_profile_handoff("/absolute/support/boot-manifest.json", support_root="/absolute/support")'
```

The host later reads/verifies this existing file and hash (`generic_host.py:13385-13409`). The built-in accepted conformance records are product inputs; they do not certify a particular Worker machine. `runtime` and Agent both require Python >=3.11 (`runtime/pyproject.toml:9`, `agent/pyproject.toml:11`); the Linux H3 engine recipe separately pins Python 3.12.10. Although generic Runtime process identity utilities have Linux support, that does not override either explicit `RoleBoundCustodyBroker` platform guard.

Smallest actionable next step for the requested Linux engine-backed Worker is a reviewed Linux custody implementation shared across the Runtime and Agent brokers, plus a non-root runner that produces the real session/profile artifacts. The existing Linux H3 provisioner can use `--placement local`; no separate engine recipe invention is necessary solely for Linux. Once custody and a real install are available, run `compose_profile_handoff(...)`, generate/bind the Worker profile path through installer/provisioner integration, and invoke Runtime loader/start. For a prompt engine-backed canary without implementation changes, provision the real profile and run on Darwin, where the two current broker checks permit this route.
