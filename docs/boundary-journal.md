# Boundary transaction journal v1

`astrid.installer.boundary_journal` is an isolated checkpoint primitive. Nothing in the installer calls it. It does not execute, authorize, replay, or reconcile any service, adoption, selection, or rollback action. It never deletes either data root. No Runtime receipt format or content is stored or invented. **Successful adoption is deliberately rejected**, so selection and registration cannot be reached in v1. A future implementation must pin and validate the actual producer contract and design a versioned receipt binding before enabling those transitions.

The caller supplies an existing, dedicated, empty journal directory and exact canonical absolute R0 and R1 paths, non-overlapping with each other and with the journal directory, an exact realm string and a canonical UUID4 operation ID. The caller must put the directory on durable storage, durably create its parent and directory before use, keep it and all ancestors private, trusted and stable (including against symlink/path replacement), serialize the entire coordinator including external effects, and retain the journal. Never put it inside either root. Roots are identity strings, not evidence of their ownership, contents, or service mapping. Use a fresh UUID per operation and do not reuse an existing directory. Cross-operation coordination and unique ID allocation are caller responsibilities.

```
j = BoundaryJournal(directory, operation_id=id, r0_root=r0, r1_root=r1, realm=realm)
j.create()                           # exclusive; refuses an existing journal
j.intent("stop")                    # must return before issuing external effect
j.effect("stop", "succeeded")      # only after independently establishing it
state = j.load()                    # state["status"]["stop"]
```

Other checkpoint names are `adopt_receipt`, `selection`, `registration`, and `rollback`. Each has a separate `intent` and `effect`; effect outcomes are `succeeded`, `failed`, or `uncertain`. Forward intents are strictly ordered and require the previous effect to have succeeded. A rollback intent can follow any state, including an unresolved intent, but does not establish that rollback is safe or that its individual manager and lock prerequisites were satisfied. An intent without a recorded effect reports `uncertain` on reload. Failed or uncertain effects cannot be upgraded or retried within the same operation. Rollback is terminal. A coordinator must refuse or independently reconcile uncertainty; this module provides no reconciliation or evidence validation.

The version 1 JSON snapshots have exactly `version`, `identity` (`operation_id`, `r0_root`, `r1_root`, `realm`) and an ordered `events` list. The numbered files start at `0000.json` and each extends its predecessor by one event. Reload strictly checks every file, schema, identity and transition. Atomic create-if-absent uses a same-directory temporary file, file fsync, hard link, unlink, then directory fsync; reload also fsyncs the directory before returning. The filesystem must support these operations and their advertised durability, including after power loss; unsupported operations fail closed. This implementation refuses to initialize outside Linux: macOS requires a separately qualified full durability protocol, and Windows directory fsync and hard-link behavior require a native implementation and qualification. Any unexpected, interrupted temporary, malformed, foreign, or missing intermediate file causes refusal. A commit exception may occur after publication; stop and inspect/reconcile, do not perform the next effect. No automatic cleanup is attempted.

An absent journal is not proof that no operation occurred. Loss or malicious removal of a valid trailing snapshot cannot be detected from this directory alone. An external durable anchor or stronger storage protocol is required to detect truncation, restore, or wholesale deletion; this primitive assumes storage is not rolled back or tampered with. It does not provide a cross-process lock or protect external actions from racing. A journal result is not a receipt, a lock lease, proof of source immutability, proof of manager state, or permission to start a service. Real integration also requires a receipt contract, ownership and lock rules, safe manager reconciliation, and native filesystem and crash testing.
