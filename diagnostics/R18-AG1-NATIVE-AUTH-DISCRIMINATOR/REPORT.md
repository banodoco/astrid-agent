The precise observed obstruction is **read access to the pinned peer's executable and namespace objects**, not lack of a pidfd API. Both user-manager and system-bus-peer proc links returned EACCES, and `PIDFD_GET_PID_NAMESPACE` / `PIDFD_GET_USER_NAMESPACE` also returned EACCES. Linux [proc link access](https://github.com/torvalds/linux/blob/v6.8/fs/proc/base.c#L1680) and [namespace link access](https://github.com/torvalds/linux/blob/v6.8/fs/proc/namespaces.c#L58) require ptrace-mode permission; newer [pidfd namespace ioctls perform the same access check](https://github.com/torvalds/linux/blob/v6.18/fs/pidfs.c#L489). The evidence does not identify which credential/dumpability/LSM condition denied access. Changing API names cannot supply missing permission or source provenance.

[SO_PEERPIDFD takes the socket's retained peer PID object](https://github.com/torvalds/linux/blob/v6.8/net/core/sock.c#L1765); [AF_UNIX copies listener credentials at connection](https://github.com/torvalds/linux/blob/v6.8/net/unix/af_unix.c#L1630). A local real-kernel delegation control demonstrated that a listening parent PID and its pidfd can differ from a child that inherits the listener and handles the request. This local control ran as root and supplies only primitive semantics, not P19 manager proof. Socket pidfd solves one race; it does not independently prove the current request-handler image or a nondelegated endpoint. systemd also explicitly labels [augmented credentials unsuitable for authorization](https://www.freedesktop.org/software/systemd/man/latest/sd_bus_creds_new_from_pid.html).
